# 0020 工具调用的时限与重复提醒

- 状态：已接受
- 日期：2026-11-12

## 背景

agent loop 有两种常见的卡死方式：

- **单次工具调用挂住**。loop 会一直等它返回，这一轮停住不动，只能由用户手动中止。`bash` 自己有超时，MCP 请求、浏览器等待也各有上限，但插件注册的工具一般没有。
- **模型反复发出完全相同的调用**。例如读同一个文件、跑同一条失败的命令，结果每次都一样，白白消耗轮次和 token，直到撞上 `maxTurns`。

DSH 用两个默认启用的插件处理这两种情况：`timeout-policy` 和 `repeat-tool-reminder`。我们照着做，挂在 [0003](0003-plugin-model-and-events.md) 留给“超时”的 `tools/execute` 扩展点上。

## 决策

### 1. 每次调用拿到自己的 `env`

- 以前 `Tools.execute` 把调用方传来的 `env` 原样交给后续流程，而 agent loop 让同一轮里所有并行调用共用这一个对象。现在 `Tools.execute` 会为每次调用复制一份 `env`（含 `callId`）。
- 这样，`tools/execute` 的监听器可以替换本次调用的 `env.signal`（比如加一个时限），返回前再恢复，不会影响并行的其他调用。

### 2. 时限（`@qianji/tool-guards`）

- `ToolDefinition` 新增 `timeoutMs` 字段：
  - 没有声明时，使用插件的默认值 10 分钟；
  - 声明为 0 表示不限时。`bash` 用自己的 `timeout` 参数控制时间，`delegate_task` 受子 agent 的轮次上限和父任务中止的约束，所以两者都声明为 0。
- 到时限后，中止本次调用的 signal，并立即向模型返回超时错误。工具不响应中止也一样，它之后返回的结果直接丢弃。
- 调用方（用户）的中止照常传给工具。

### 3. 重复提醒

- 同一个会话连续发出同一工具、同样参数的调用时，在第 3、5、8 次调用的结果后附加一条提醒，说明结果不会变。第 8 次的措辞最强，要求模型停下来，向用户说明卡在哪里。
- 判断参数是否相同时会先把键排序，键的顺序不同也算同一个调用。
- 只是提醒，不拦截调用。
- 每个会话分开计数，内存里最多记 500 个会话。

## 后果

- 挂住的插件工具最多拖住一轮 10 分钟，之后模型会收到明确的错误，可以换别的做法。
- 不响应中止的工具到时限后仍会在后台运行，只是结果被丢弃。真正停止它要靠工具自己响应 `signal`。
- 合理的轮询（例如反复截图等页面变化）也可能被提醒。提醒只是建议，模型可以说明理由后继续。

## 备选方案

- **只给声明了 `timeoutMs` 的工具设时限**（DSH 的做法）：我们自带的工具大多已经有各自的上限，真正需要兜底的是没有声明时限的插件工具，所以改成默认给所有工具设时限，个别工具再声明不限时。
- **重复时直接拒绝调用**：轮询这类合理的重复会被误伤，提醒的代价更小。否决。
